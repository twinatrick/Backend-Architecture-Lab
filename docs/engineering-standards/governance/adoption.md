# 採用與發布治理

狀態：已於 `0.1.0` 正式發布。前後端專案以鎖定版本之完整快照與 commit 進行集中接軌。

## 權威、適用範圍與修改

正式採用後，適用要求為「鎖定版本的共通底線 + 技術 Profile + 已核准專案例外」。專屬要求可以細化或加嚴，不可暗中降低共通底線。互斥要求先提交使用者裁決，不能用「較嚴優先」掩蓋衝突。

規範只能回本庫修改。原專案 `開發規範.md` 為入口，保留完整快照；業務詞彙與既有 ADR 留原地。原專案 AGENTS 保留執行環境、指令與安全限制，不再另訂相互競爭的工程規則。

## 單一版本與鎖定採用

本庫整體使用同一發布版本，後端與前端各自選版本及 Profile，不要求同步升版。草案編號不是正式 tag，不得填入虛構 commit SHA。

消費端 `docs/engineering-standards/manifest.json` 記錄來源 HTTPS URL、版本、不可變 Git commit SHA、Profile、每個來源路徑／本地路徑與 SHA-256。正式採用不得只有 URL、branch 或檔案雜湊。

匯入時應由可信公開遠端核對不可變 commit，核對發布版本與該 commit 的關係，再核對該提交的清單及檔案內容。離線檢查只讀取本地檔案，不代表已完成此核對。

## 發布與升版

1. 核對來源提交、授權、第三方聲明及公開脫敏，記錄審核者與證據。
2. 核准規範內容、衝突處理及改善提案；未核准提案不得混入強制基準。
3. 檢查連結、清單及測試；經使用者明確授權才 commit、tag、建立公開遠端或 push。
4. 標準庫有真實 commit 後，以該 SHA 匯出正式快照；消費端確認來源真實性並核准升版。
5. 核對本地完整快照、版本差異、遷移影響與所有例外，確認後才切換入口權威。

不自動更新套件、不變更兩端品質工具設定、不將快照檢查接入 CI／hooks。匯出工具遇到不同版本或異動檔案應拒絕覆寫；升版經人工檢視後另行處理，不以強制覆蓋取代審查。

## 例外紀錄

每筆專案例外記錄在專案 `docs/engineering-standards/exceptions.md`，不修改快照原文：

| 欄位 | 必填內容 |
| --- | --- |
| 識別碼與規範定位 | 規範版本、來源檔案、條文及 Profile |
| 範圍 | 適用專案、程式位置、影響對象 |
| 原因與影響 | 無法符合的原因、風險及降低的底線 |
| 替代措施 | 可驗證措施、驗證方式及負責人 |
| 核准 | 使用者或指定核准者、日期與證據 |
| 期限 | 到期日或明確重審條件，不接受無條件永久例外 |
| 升版重審 | 採用新版本前重新核准、撤銷或遷移 |

尚未核准的申請不構成例外；既有工具遷移白名單不自動等同本治理流程的核准例外。

## 改善提案必要資訊

提案需列問題與效益、適用範圍、擬定強制／建議等級、驗證方式、導入成本、遷移影響及使用者核准狀態。發現缺口不等於授權立即修改工具或業務程式碼。
