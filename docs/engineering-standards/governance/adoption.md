# 採用與發布治理

狀態：本文件以 `0.1.0` 已發布治理為基礎，納入 `0.2.0` 正式修訂；不追溯改寫既有快照。

## 權威、適用範圍與修改

正式採用後，適用要求為「鎖定版本的共通底線 + 技術 Profile + 已核准專案例外」。專屬要求可以細化或加嚴，不可暗中降低共通底線。互斥要求先提交使用者裁決，不能用「較嚴優先」掩蓋衝突。

規範只能回本庫修改。原專案 `開發規範.md` 為入口，保留完整快照；業務詞彙與既有 ADR 留原地。原專案 AGENTS 保留執行環境、指令與安全限制，不再另訂相互競爭的工程規則。

## 單一版本與鎖定採用

本庫整體使用同一發布版本，後端與前端各自選版本及 Profile，不要求同步升版。草案編號不是正式 tag，不得填入虛構 commit SHA。

消費端 `docs/engineering-standards/manifest.json` 記錄來源 HTTPS URL、版本、不可變 Git commit SHA、Profile、每個來源路徑／本地路徑與 SHA-256。正式採用不得只有 URL、branch 或檔案雜湊。

首次採用與每次升版須透過可信管道核對規範庫身分、正式版本與不可變 commit 的對應，以及該提交的清單及檔案內容，並確認版本未撤回。可信管道包含已驗證身分的私人庫存取，不要求公開。離線檢查只讀取本地檔案，不代表來源已認證、版本仍可新採用或沒有已知規範缺陷。

## 發布階段與合規相容性

內容核准、版本發布與專案採用是獨立狀態。正式發布不要求先有消費端採用，也不宣稱已驗證消費端相容性；發布說明須列適用範圍、不相容要求、遷移影響與未驗證部分。

`draft` 為未發布草案，`prerelease` 為已發布但僅供試採用的預發布版本，`published` 為可供申請正式採用的正式版本。預發布與正式發布皆須完成授權、衝突及公開脫敏門禁；未完成只能保留草案。正式版本須符合 SemVer 且不得有預發布標記；預發布須有標記，不能靠把 `rc` 標成 `published` 取得正式資格。

若新版使舊版下原本合規的實作不再合規，即屬不相容變更，不以產品 API、執行行為或修改成本判定。新增強制要求、收窄例外、建議升為強制均須評估。`0.x` 階段不相容變更升次版；修訂版不得新增合規義務。自 `1.0.0` 起，不相容變更升主版。

已發布內容與版本／提交對應不可原位修改，不可重用版本或移動既有 tag；錯字與連結修正也另發新版，依實際合規影響選版號。撤回資訊另行發布，不修改舊快照；停止新採用並通知已知採用端，由各端確認收到並評估遷移、回退或限期例外。撤回不自動切換有效基準，也不直接判定整個專案違規。

## 發布與升版

1. 核對來源提交、授權、第三方聲明及公開脫敏，記錄審核者與證據。
2. 核准規範內容、衝突處理及改善提案；未核准提案不得混入強制基準。
3. 檢查連結、清單及測試；經使用者明確授權才 commit、tag、建立公開遠端或 push。
4. 標準庫有真實 commit 後，以該 SHA 匯出正式快照；消費端確認來源真實性並核准升版。
5. 核對本地完整快照、版本差異、遷移影響與所有例外，確認後才切換入口權威。

各項可由具權限的維護者一次明列核准，不要求額外多人覆核；未提及事項不視為通過。核准須綁定可識別的候選內容與版本；後續變更須列差異及影響，重審受影響事項，未受影響結果可附理由沿用。最終核准必須涵蓋實際發布內容，不要求將提交自身 SHA 寫回同一提交。發布審查不推定授權 commit／tag／push，也不推定消費端採用。

不自動更新套件、不變更兩端品質工具設定、不將快照檢查接入 CI／hooks。匯出工具遇到不同版本或異動檔案應拒絕覆寫；升版經人工檢視後另行處理，不以強制覆蓋取代審查。

## 隔離準備與受控切換

1. 草案與預發布僅能試採用，匯出必須指定 `--preview`，寫入 `docs/engineering-standards-preview/<版本>/<Profile>/`；不替換有效快照、正式入口或檢查器，差異檢查不得把候選要求變成正式阻擋基準。
2. 正式匯出只準備 `docs/engineering-standards-candidates/<版本>/<Profile>/`，不執行採用或原位更新。工具核對提交存在，以及 catalog 所列全部檔案、catalog 本身、匯出器與檢查器的位元組均與指定提交一致；快照由已核對內容產生。無關檔案的本機變動不構成拒絕理由。此核對不證明遠端身分、授權或品質。
3. 候選內含獨立 `check_snapshot.py` 及 manifest；先在暫存候選完成驗證，再移入隔離位置。同一位置已有不同內容時拒絕覆寫；`--update` 已停用。既有有效快照須先通過完整性核對，若遭修改，保留現場，釐清後將合理差異轉為集中修訂或專案例外，不能以升版授權丟棄異動。
4. 正式升版前，每項適用要求須已符合或有有效核准例外，所有既有例外重新審查。不符合時維持舊版繼續試採用，不能混用新舊條文作基準。
5. 消費端在受控、可回復的變更中一併準備快照、正式檢查器及入口，先保存舊有效基準與回復方式，再切換並驗證版本、Profile、檔案、入口與檢查器一致。必要驗證通過後才記錄採用完成；中途失敗應保留或恢復舊基準，無法確認一致性時明示失敗，不宣告成功。匯出器不自動執行這個切換。
6. 歷史 `0.1.0` 快照保持不變，不因缺少後增治理資料自動失去既有採用資格。新版檢查器可用 `--checker-file` 只讀核對歷史檢查器雜湊，不執行舊檔；新的匯出與升版仍須符合新防護。

本版發布前須完成上述工具限制、測試與操作文件；不新增 CI、聯網認證、簽章平台或自動審批系統。完整性以原始位元組判定，換行轉換亦屬內容變更，不自動正規化、修復或覆寫。

## 例外紀錄

每筆專案例外記錄在專案 `docs/engineering-standards/exceptions.md`，不修改快照原文：

| 欄位 | 必填內容 |
| --- | --- |
| 識別碼與規範定位 | 規範版本、來源檔案、條文及 Profile |
| 範圍 | 適用專案、程式位置、影響對象 |
| 原因與影響 | 無法符合的原因、風險及降低的底線 |
| 替代措施 | 可驗證措施、驗證方式及負責人 |
| 核准 | 使用者或指定核准者、日期與證據 |
| 期限 | 到期日或明確重審條件，不接受無條件永久例外 |
| 升版重審 | 採用新版本前重新核准、撤銷或遷移 |

尚未核准的申請不構成例外；既有工具遷移白名單不自動等同本治理流程的核准例外。

例外到期或重審條件成立而未續准即失效，不默認延長。仍未符合的相關要求與實作範圍恢復不合規判定，不擴張成整個專案全面違規；續准須重新評估並明確核准。集中庫定義判定與必要揭露，各消費端核准 CI／部署如何阻擋；只告警或沒有自動阻擋不代表已合規，也不授權工具自動改碼或回退。

## 改善提案必要資訊

提案需列問題與效益、適用範圍、擬定強制／建議等級、驗證方式、導入成本、遷移影響及使用者核准狀態。發現缺口不等於授權立即修改工具或業務程式碼。
