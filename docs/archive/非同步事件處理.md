# Kafka 非同步事件處理與訊息佇列架構 🆕

本專案採用 **Kafka** 消息佇列（Message Queue）作為微服務架構中高性能、低延遲的事件驅動與非同步解耦核心。透過良好的主題（Topic）劃分與監聽配置，不僅平滑地承載了感測設備的高併發上傳，也優化了分散式事務的補償與性能統計。

---

## 🗺️ 一、 核心設計與架構價值

在微服務架構中，部分高耗時、高 IO 或是非同步推送的邏輯不應與 Web 請求線程（Tomcat Thread Pool）強耦合。Kafka 在本系統中主要提供以下三大價值：

1. **非同步解耦**： Alert 服務解析感測設備數據與前端即時推送 WebSocket 邏輯完全分離，避免持久化資料庫與網頁連線推送相互阻塞。
2. **高併發緩衝（削峰填谷）**：將設備端上傳的突發大流量排隊緩衝，避免直接癱瘓後端 API 服務與資料庫。
3. **資料最終一致性（Saga 補償模式）**：在跨服務操作中（如 IAM 與 Competency），當某一步驟發生異常時，透過 Kafka 事件非同步通知補償機制，執行資料回滾補救。

---

## 📬 二、 Kafka 主題（Topics）與業務場景規格

系統中當前活躍運行三大核心主題，均各自對應其專屬的業務與資料序列化規則：

### 1. 即時告警廣播 (`socketSend`)
* **生產端（Producer）**：`AlarmKafkaPublisher`（位於 `backend-alert-service`）
* **消費端（Consumer）**：`KafkaConsumerService`（位於 `backend-alert-service`）
* **資料封包**：`List<AlarmMessage>`（採用批量 JSON 封包傳輸）
* **業務場景**：
  * 當 Alert 服務中的檢測機制發現感測器數值異常（觸及警報限額）時，會將警報訊息封裝並發送至 `socketSend` 主題。
  * `KafkaConsumerService` 通過批量監聽拉取該列表，調用 `AlarmWebSocket.broadcast` 將告警訊息推送到所有在線上的網頁客戶端，實現即時且非阻塞的警報視覺化呈現。

### 2. 分散式交易補償 (`transaction-compensation`)
* **生產端（Producer）**：各微服務業務組件（如 IAM、Competency 服務等）
* **消費端（Consumer）**：`CompensationConsumer`（位於 `backend-alert-service`）
* **資料封包**：`CompensationEvent`（包含交易 ID `transactionId`、操作名稱 `action`、狀態 `status`）
* **業務場景**：
  * 當系統進行跨多個資料庫與微服務的操作（例如「專案成員技能重新綁定 `PROJECT_MEMBER_SKILLS_REBIND`」）時，若在後續步驟中發生失敗，則會向此主題發送 `COMPENSATED` 狀態事件。
  * `CompensationConsumer` 監聽到該事件後，會根據 `action` 與 `transactionId` 執行對應的補償逻辑，如手動進行反向操作或清除暫存狀態，確保系統的最終一致性。

### 3. 快取統計指標收集 (`cache-stats`)
* **生產端（Producer）**：各子服務的二級快取切面與 AOP 攔截器（IAM、Competency、Job 等服務）
* **消費端（Consumer）**：`CacheStatsConsumer`（位於 `backend-alert-service`）
* **資料封包**：`CacheStatsEvent`（包含快取名稱 `cacheName`、操作屬性 `field` 如 hit/miss/bloom-block）
* **業務場景**：
  * 各子服務在處理快取命中（Hit）、快取未命中（Miss）或被布隆過濾器（Bloom Filter Block）攔截時，會非同步向 `cache-stats` 主題發送事件。
  * `CacheStatsConsumer` 監聽到此事件後，調用 `StringRedisTemplate.opsForHash().increment` 對 Redis 中的雜湊鍵 `cache:stats:<cacheName>` 進行原子自增累加。
  * Alert 服務的 `AlertController` 透過 `/cache-stats` 端點，將 Redis 中積累的命中率指標整合呈現，提供監控看板數據。

## ⚙️ 三、 精密配置與元件設計

系統的 Kafka 配置主要由 `backend-alert-service` 下的 `KafkaConfig` 統一載入：

### 1. 環境自適應配置（Bootstrap Servers）
為確保開發與容器化部署能「一鍵運行」，`KafkaConfig` 內部提供自動解析路徑機制：
```java
package com.example.BackendArchitectureLab.Config;

public class KafkaConfigExample {

    private String configuredBootstrapServers;
    private boolean inDocker;

    private String resolveBootstrapServers() {
        if (configuredBootstrapServers != null && !configuredBootstrapServers.isBlank()) {
            return configuredBootstrapServers;
        }
        // 依據 APP_IN_DOCKER 環境變數自動適配
        return inDocker ? "kafka:9092" : "localhost:9092";
    }
}
```

### 2. 消費者群組與負載均衡（Consumer Group）
* 預設統一使用消費者群組：`myGroup`（由 `kafka.consumer.group-id` 配置項指定）。
* 同一消費者群組下的多個服務實例可以共同分攤分區（Partition）的消息，實現負載均衡。

### 3. 專屬 Container Factory 設置
為應對不同的資料型別反序列化需求，配置類別中聲明了專屬的監聽容器工廠：
* `alarmMessageKafkaListenerContainerFactory`：專用於解析 `List<AlarmMessage>`，配置有 Jackson 泛型 `TypeReference` 與信任套件，防止反序列化攻擊。
* `cacheStatsKafkaListenerContainerFactory`：專用於解析單一的 `CacheStatsEvent` JSON 物件。

## 🛡️ 四、 可靠性與異常處理機制

1. **批量與容錯機制**：
   * 在 `alarmMessageKafkaListenerContainerFactory` 中配置了 Spring Kafka 的 `DefaultErrorHandler`（異常處理器）。
   * 當反序列化出錯或業務監聽中途拋出未捕獲異常時，`DefaultErrorHandler` 會介入並記錄錯誤日誌，避免單一問題訊息造成消費循環堵塞。
2. **自動重試**：
   * 內建的消費配置會根據偏移量（Offset）手動/自動提交策略來確保訊息的可靠傳輸，提供 "At-least-once"（最少一次）的傳遞保證，杜絕告警與補償事件在傳輸中遺失。
