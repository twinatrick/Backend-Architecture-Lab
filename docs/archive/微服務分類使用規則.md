# 微服務分類使用規則

## 核心原則

### 1. 服務邊界與職責歸屬

#### 1.1 服務職責清單
| 服務 | 負責領域 | 核心實體 |
|------|----------|----------|
| `iam-service` | 使用者認證、全局權限、使用者與角色管理 | User、Role、Function、UserRole、RoleFunction |
| `competency-service` | 專案與能力管理 | Project、Skill、SkillLevel、UserProject、UserSkill、UserProjectSkill |

- 各服務**只允許操作自身職責清單內的實體與資料表**
- `iam-service` 唯獨負責使用者認證、全局權限與 User 核心實體，**絕不能感知上層業務**

#### 1.2 依賴方向（單向，不可逆）
```
competency-service (業務) ──Feign──▶ iam-service (IAM)
```
- **業務服務**（如 `competency-service`）可以透過 Feign Client 呼叫 **IAM**
- **IAM 絕對禁止依賴或呼叫任何業務服務**，包含但不限於：
  - 注入業務服務的 Feign Client（如 `CompetencyProjectFeignClient`）
  - 操作業務服務的快取命名空間（如 `projects`）
  - 引用業務服務的型別（如 `UserProjectBindRequest`、`IProjectService`、`ISkillService`）

#### 1.3 禁止反模式
- ❌ **跨服務環狀呼叫**：competency → IAM → competency（如 IAM 內提供 `/users/inner/rebind-projects` 回呼 competency）
- ❌ **IAM 操作業務快取**：如 `@CacheEvict(value = "projects", ...)`
- ❌ **業務介面/幽靈依賴殘留 IAM**：無實作、無引用的業務 Service 介面不得存放於 IAM
- ❌ **同服務自我 Feign 呼叫**：服務內部邏輯應注入自己的 Service 介面，不得用 Feign 打自己
- ❌ **IAM 內含業務綁定邏輯**：如 user-project 綁定應由 competency 的 `UserProjectService` 管理
- ❌ **僅供自我呼叫的 Feign Client**：若 Feign Client 只被同服務自己呼叫（打到自身 instance，如 `CompetencySkillFeignClient`），應改為注入本地 Service 介面並移除該 Client
- ❌ **無消費者的幽靈 Feign Client / 幽靈 Service 介面**：不得保留任何服務未注入使用的 Feign Client（如 `AlertCheckLimitFeignClient`）或無實作、無引用的 Service 介面（如 `IBloomFilterService`）
- ❌ **權限驗證自我 Feign / 反射繞過**：IAM 內部的權限驗證應實作 common 的 `LocalPermissionValidator`（本機方法呼叫），禁止以反射或 Feign 自我呼叫 `/role/inner/validate`；其餘服務維持預設 `DefaultPermissionValidator`（Feign → IAM）

### 2. 模組資料隔離
- 每個微服務模組**只能查詢屬於自己模組的資料表**
- 嚴禁跨模組直接查詢資料庫（如：`competency-service` 不可查詢 `users` 表）
- 跨服務資料存取一律透過 **Feign Client** 呼叫對應服務的 API

### 3. 層級職責劃分

```
Controller → Service → DataAccess → Repository → JPA
```

- **Controller 層**：請求接收與回應
- **Service 層**：業務邏輯，**禁止直接使用 `EntityManager`**
- **DataAccess 層**：資料存取抽象，可使用 `EntityManager` 作內部實作
- **Repository 層**：Spring Data JPA 介面

### 4. 跨服務關聯處理

#### 外鍵參考（FK Reference）
- 需要在本地實體設定跨服務 Entity 的外鍵時，使用 `new Entity()` + `setId()` 方式：

```java
package com.example.BackendArchitectureLab.Service.Impl;

import com.example.BackendArchitectureLab.Entity.User;
import com.example.BackendArchitectureLab.Entity.UserProject;
import java.util.UUID;

public class MicroserviceFkExample {

    // 正確：只設定 ID，不查詢其他服務的資料表
    public void bindUserProject(UUID userId, UserProject userProject) {
        User user = new User();
        user.setId(userId);
        userProject.setUser(user);
    }
}
```

- 此方式不會觸發資料庫查詢，僅提供 JPA 所需的 FK 值

#### 資料驗證
- 驗證跨服務 Entity 是否存在時，使用 Feign Client：

```java
package com.example.BackendArchitectureLab.Service.Impl;

import com.example.BackendArchitectureLab.FeignClient.UserServiceFeignClient;
import lombok.RequiredArgsConstructor;
import java.util.UUID;

@RequiredArgsConstructor
public class MicroserviceValidationExample {

    private final UserServiceFeignClient userServiceFeignClient;

    public void validateUser(UUID userId) {
        if (!userServiceFeignClient.existsUserById(userId)) {
            throw new IllegalArgumentException("User not found");
        }
    }
}
```

### 5. 使用 EntityManager 的限制

| 層級 | 是否允許 | 說明 |
|------|----------|------|
| Service | ❌ 禁止 | 業務邏輯不應直接操作持久層 |
| DataAccess | ✅ 允許 | 可作為內部實作細節使用 |
| Repository | ✅ 允許 | Spring Data JPA 底層 |

### 6. 實體共用規則
- 共用 Entity 定義放在 `backend-common` 模組
- Entity 僅供 JPA 映射參考，**不應作為跨服務資料傳輸載體**
- 跨服務資料傳輸使用 Vo 與 Feign Client

### 7. JPA 關係設定
- 跨服務的 `@ManyToOne` / `@OneToMany` 關係不設定 `cascade`
- EAGER fetch 應謹慎使用，避免觸發跨服務資料表查詢
