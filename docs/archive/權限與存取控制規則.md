# 權限與存取控制規則

本文件規範本專案（微服務架構）的權限設計。權限字典為唯一真源：所有在 Controller 使用的權限，**必須**能在權限字典中找到對應的定義；反之字典中**禁止**保留任何沒有 Controller 使用的權限（幽靈權限）。

## 1. 三層權限結構

權限路徑由三個層次組成，實際存入 IAM 的 `function` 資料表：

```
{第一層：微服務} / {第二層：資源層 layer()} / {第三層：動作層 value()}
```

| 層 | 來源 | 範例 |
|----|------|------|
| 第一層：微服務 | 由服務本身決定（Gateway / 驗證端固定） | `Iam`、`Competency`、`Job`、`Alert`、`ExternalApi` |
| 第二層：資源層 | `@RequirePermission(layer = "...")`，未寫時**預設 = Controller 類名去除「Controller」後綴** | `User`、`Skill`、`ProjectManagement` |
| 第三層：動作層 | `@RequirePermission("...")`（value） | `View`、`Edit` |

## 2. 動作層字串規範（第三層）

- `View` = 讀取操作。
- `Edit` = 寫入操作（新增 / 更新 / 刪除 / 綁定 / 重新綁定均屬之）。
- 特殊例外（保留且需字典定義）：`Create`（UserController 建立使用者）、`Scrape`（JobPostingController 爬取分析職缺）。
- **禁止個人語義變體**：如 `PersonalEdit`、`EditAll` 一律不得使用，統一以 `Edit` 取代。所有端點（含個人專案 / 個人技能 / 管理員批量操作）均以 `View` / `Edit` 兩態區分。

## 3. 權限字典（唯一真源 & 幽靈權限禁令）

- 字典位於 IAM 服務 `InitAndCheckService.checkFunctionBindDefaultRole()`，以 `List.of(...)` 定義全部權限；IAM 啟動時會檢查並自動補建缺失的 function。
- **行動字典只增不減、需可追蹤，不得預留**：字典中任何一筆權限都必須有對應的 `@RequirePermission` 使用；確認沒有 Controller 使用者時，必須同步從字典與 Controller 移除。
- 新增權限流程：控制器新增 `@RequirePermission(...)` 的同時自行維護字典；兩邊同步完成，不得只改一邊。

## 4. 第二層覆寫範例

預設層（類名轉換）：

```java
@RestController
@RequestMapping("/skill")
public class SkillController {              // 第二層自動為 "Skill"
    @RequirePermission("View")
    public ... getAll() { ... }
}
```

自訂層（控制器名稱與資源層命名不同時覆寫）：

```java
@RestController
@RequestMapping("/project/admin/bindings")
@RequirePermission(layer = "ProjectManagement")   // 覆寫 "ProjectAdmin" → "ProjectManagement"
public class ProjectAdminController {
    @RequirePermission("Edit")                    // 路徑 = Competency / ProjectManagement / Edit
    public ... rebind() { ... }
}
```

## 5. 自助 vs 管理（准入策略）

| 情境 | 作法 |
|------|------|
| 管理層操作（CRUD、批量管理他人資料） | 方法標註 `@RequirePermission("View" / "Edit")` |
| 自助端點（操作「當前登入使用者」自己的資料） | 使用 `SecurityUtil.requireCurrentUserId()` 取得目前使用者的 ID 進行操作（如 `/user/bindings`、`/skill/personal`） |

- 自助端點仍可（可選）加上 `@RequirePermission` 控制可存取對象，但決定權在當前使用者身分，確保不能操作其他人的資料。
- 管理端點一律必須驗證權限（`@RequirePermission`），禁止以裸身分執行管理操作。

## 6. BOLA（物件層級授權）防護

- 以 ID 存取資源（依路徑 `{id}`）時，若資源為「個人所屬」或「操作需擁有者才能執行」，一律要驗證 `SecurityUtil.requireCurrentUserId()` 與資源擁有者是否一致（參考 `VoiceUploadController` 的 `requireCurrentUserId().equals(upload.getUserId())` 寫法）。
- 驗證失敗一律拋出例外（`AppException` / `IllegalStateException`），禁止直接回傳資料。

## 8. 未定義動作層（不可出現）

以下字串**不得**再出現在 `@RequirePermission`、權限字典或任何權限文件中：

- `PersonalEdit`（已併入 Edit）
- `EditAll`（已併入 Edit）
- `SkillManagement`、`RolePermission`、`AquarkDataAvg`、`LimitSetting`（幽靈權限已移除）
